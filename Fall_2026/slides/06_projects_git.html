Segment 2 · 3–8 min

Reading a file

import pandas as pd

df = pd.read_csv("data/raw/patients.csv")
df.head()
df.dtypes      # ← check the types!

library(readr)

df <- read_csv("data/raw/patients.csv")
head(df)
str(df)        # ← check the types!

Session 2's habit, now with real data

df.dtypes / str(df) is where you catch the age column that loaded as text, before it poisons everything downstream. Run it every single time you load a file.

Relative paths, always

Absolute — will not run anywhere else

"/Users/josh/Desktop/CPBP/data/patients.csv"

"C:\Users\dan\Documents\proj\data\patients.csv"

Breaks on the TA's machine, on a cluster, and on your own laptop after you reorganize your Desktop.

Relative — travels with the project

"data/raw/patients.csv"

“From wherever this is running, go into data, then raw, and open the file.” Works for anyone who has the folder.

“Wherever this is running” is the working directory: os.getcwd() in Python, getwd() in R.

RStudio .Rproj files set it for you. Jupyter uses the notebook's own folder. VS Code sometimes uses the folder you opened — which is why your path “randomly” stops working.

Segment 3 · 8–14 min

A project folder someone else can read

your-project/
├── README.md          ← what is this? how do I run it?
├── .gitignore         ← what Git should ignore
├── data/
│   ├── raw/           ← original files. NEVER edited.
│   └── processed/     ← cleaned versions your code produces
├── scripts/
│   ├── 01_clean.py
│   ├── 02_eda.py
│   └── 03_stats.py
├── notebooks/         ← .ipynb for exploration
├── figures/           ← output plots
└── output/            ← tables, models, everything else derived

Four rules, stated out loud

  1. Never edit anything in data/raw/. Ever. It is your source of truth. Cleaning produces a new file in processed/.
  2. Number scripts that run in order. 01_clean before 02_eda. That numbering is documentation for future-you.
  3. A README is not optional. Three paragraphs: what this is, how to run it, what data you need.
  4. Figures and outputs are derived. You should be able to delete figures/ and regenerate it by running your scripts.

Rule 4 is a test, not just advice

Delete your figures folder and re-run. If you can't rebuild it, your analysis is not reproducible yet — and you have just found out cheaply instead of during peer review.

Segment 4 · 14–24 min

Git's mental model

Working dirYour actual files, as you are editing them right now.
→ git addStaging areaChanges you've selected to go into the next snapshot.
→ git commitLocal repoA permanent, named snapshot on your machine.
→ git pushGitHubA copy of that history on the internet.

Git is the version-control system. GitHub is just a website that stores a copy. They are not the same thing, and you can use Git with no internet at all.

The four commands that cover 90% of this course

git status                          # what has changed since the last commit?
git add .                           # stage everything that changed
git commit -m "add outlier filter"  # snapshot it, with a message
git push                            # send it to GitHub

That is the loop. You will run it several times per work session.

Everything else in Git — branches, rebasing, merge conflicts — is real and useful and not your problem this semester.

Live demo — follow along

  1. git init — this folder is now a repo
  2. Edit scripts/01_clean.py
  3. git status — Git notices the file is modified
  4. git add scripts/01_clean.py — stage just that file
  5. git commit -m "add outlier filter" — snapshot
  6. git log --oneline — your history so far
  7. Break the script on purpose
  8. git diff — Git shows exactly what changed
  9. git restore scripts/01_clean.py — undone.
git restore <file> is the modern spelling. git checkout -- <file> does the same thing and is what you'll see in older tutorials and on the final quiz.

Commit before you paste AI-generated code.

When the model rewrites half your script and it stops working, git restore is instant, total, guaranteed undo.

Without a commit, your only undo is Ctrl-Z and your memory.

When to commit, and what to say

Commit when

  • You're about to start something new — capture the good state
  • Before pasting AI code that touches more than a few lines
  • You just got something working
  • You're closing the laptop

3–10 commits per productive hour is normal for research code. Not one per week.

Message hygiene

  • Imperative present: “add outlier filter”, not “added” or “adding”
  • Specific: “fix mean-BP calc to skip NA” beats “fix bug”
  • One logical change per commit

The message is a note to yourself in three months, when you need to find the commit that changed a number in your paper.

Segment 5 · 24–30 min

.gitignore — and the things you must never commit

# .gitignore
.DS_Store
__pycache__/
*.pyc
.Rhistory
.Rproj.user/
env/
.env
*.log

data/raw/*.csv     # if private or large

Never commit

  • Patient / identifiable data
  • API keys and passwords
  • Files over ~100 MB
  • Files that change on every run

Understand this before you push

Deleting a file in a later commit does not remove it from the history. If you commit a patient file or an API key and push it, treat it as permanently exposed: rotate the key, tell your PI. Cleaning it out properly is genuinely hard.

Getting onto GitHub

  1. Sign in at github.com → New repository.
  2. Name it to match your local folder. Private is fine — and is the right default if your data is at all sensitive.
  3. Do not check “Add a README” — you already have one locally, and it will conflict.
  4. Copy the two commands GitHub shows you and run them in your project folder:
git remote add origin https://github.com/YOU/your-project.git
git push -u origin main
GitHub will ask you to authenticate. Use a personal access token or the GitHub CLI (gh auth login) — your account password will be rejected.
